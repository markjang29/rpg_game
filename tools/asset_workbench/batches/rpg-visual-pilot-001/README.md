# RPG-VISUAL-PILOT-001: 첫 RPG 시각 자산 생산 묶음

상태: 실행 완료(2026-11-19) — 12+2(보정) 생성 / 후보 6 선별 / 격리 화면 반입 증거 확보. 상세는 results.json.
기존 워크벤치의 실제 /api/generate 입력 계약을 사용한다. 신규 생성 서비스나 게임 메커니즘을 추가하지 않는다.

## 목표와 범위
전투 이펙트 4, 아이템 4, 배경 2, 장비 2개 후보를 생성하고, 독립 시각 검수를 통과한 후보 최소 6개와 격리 게임/미리보기 반입 증거 1개를 남긴다. 이름 있는 캐릭터와 세계관 설정은 추가하지 않는다. 모든 결과는 초안이며 정식 승격은 기존 채택 절차를 유지한다.
색상은 기존 워크벤치 classic의 slate/mint를 공통 기준으로 쓴다. 아이템 구분을 위해 amber, violet, pale blue 보조색을 사용한다. 기존 앱은 이펙트를 정지 PNG로 생성한다. 애니메이션, 스프라이트, 투명 PNG, 타일링 배경으로 완성됐다고 보고하지 않는다.

## 담당과 착수
- 매니저: 기존 진행 작업/중복 배치 확인 후 준비된 작업을 한 건씩 배정. 이 문서/PR 존재를 접수로 간주하지 않는다.
- RPG/자산 생성 담당: 기존 워크벤치와 저장소를 재사용해 생성, 실제 결과와 요청 ID를 매핑.
- 별도 검수 담당: 시각 품질, 메타데이터, 실제 사용처를 확인.
- z.ai 작업 범위: 프롬프트 보정, 실패 분석, 필요한 최소 반입 코드/검사, 메타데이터 정리. 새 관제·전면 리팩토링은 이 묶음의 선행 조건이 아니다.
- 사용자에게 매 이미지·매 단계의 선택을 다시 요구하지 않고, 이 요청 범위의 가역적 초안과 기술검사를 수행한다. 정식 세계관 채택·배포·추가 지출은 별도 결정이다.

## 실행 절차
1. 기존 진행 중 생성 배치가 있는지 확인하고 중복이면 그 배치에 이 job_id를 연결한다. 현재 서비스 코드/모델/무료 생성 가능 조건을 확인한다. 비밀 값은 파일·로그·PR에 옮기지 않는다.
2. batch.json을 validator로 검사한다. 워크벤치 코드가 바뀌었으면 계약을 다시 대조한다.
3. 요청 01과 05를 한 번씩 생성해 파일, 모델, 0 Anlas 조건, 스타일·가독성을 확인한다. 추가 Anlas 차감 가능성이 있거나 무료 조건이 확인되지 않으면 생성 호출만 보류하고 나머지 텍스트·검수 작업을 계속한다.
4. 나머지 10건을 동시성 1로 생성한다. 각 request 객체를 기존 POST /api/generate에 전달하고 기존 인증 경로를 사용한다. 주소·키를 이 문서에 새로 하드코딩하지 않는다. batch 전체를 API에 그대로 보내지 않는다.
5. 반환된 WB-* ID, 파일 경로와 해시를 job_id별로 기록한다. 기존 WB ID와 중앙 CHR/DRF ID를 혼동하지 않는다. 중앙 자산 ID는 기존 등록 절차가 부여하며 임의 예약하지 않는다.
6. 효과/아이템은 64px 축소에서도 구별되는지, 배경은 중앙 게임/UI 영역을 가리지 않는지 실제 화면에서 검수한다. 후보 최소 6개 선별. 결함 보정은 총 6회 이하, 동일 원인 2회 실패면 blocked로 표시하고 독립된 다음 슬롯 진행.
7. 한 후보를 격리된 기존 미리보기/게임 경로에 반입해 화면 증거를 남긴다. 새 게임 시스템·전투 숫자·정식 채택은 변경하지 않는다. 반입 어댑터가 없으면 generated/reviewed까지만 보고하고 exact blocker를 남긴다.
8. 다른 검수자가 파일과 사용처를 확인한 후 배치 결과를 제출한다. 다음 묶음은 부족한 종류를 채우며, 사용처 없는 수백 장 생성은 하지 않는다.

## 비용·복구 계약
기준 코드는 nai-diffusion-4-5-full, steps=28, n_samples=1, text-to-image, 832×1216 또는 1024×1024이다. 실제 구독/모델 조건에서 0 Anlas인지 운영 담당자가 먼저 확인한다. Opus 영수증만으로 현재 구독 상태와 무료 적용을 보장하지 않는다. V5 전환·유료 확대·quota reset·image-to-image·업스케일을 자동 실행하지 않는다.
기존 워크벤치 POST는 명령 멱등키를 받지 않고, WB ID 할당도 파일 스캔 방식이다. 따라서 한 번에 하나만 실행하고, 응답 유실/timeout은 unknown으로 둔다. 저장된 메타데이터의 seed/type/extra와 파일을 대조하기 전 재전송하지 않는다. seed는 추적 보조값이며 API 멱등성 보장이 아니다.
세션이 바뀌면 결과 대장에서 미제출/미확인 job만 이어받는다. 실패를 성공으로 채우거나 작업 ID를 새로 만들어 중복 생산하지 않는다.

## 증거 형식
job_id / request_hash / actual WB ID / source asset ref(있으면) / output PNG / sha256 / actual model / seed / size / Anlas before-after 또는 무료 판정 근거 / generated_at / review status+reason / reviewer / preview proof.
없으면 null 또는 not_run. 0장을 생성했으면 생성 0이라고 쓴다. 생성·기술검수·사용자 채택·runtime 반입을 별도 집계한다.
검수자는 ‘한눈에 구별되는가’, ‘우리 화면에서 쓰이는가’, ‘재생성 근거가 남는가’를 본다. 보고는 합성 미리보기 한 장+사용처+합격/반려 수+막힘 한 줄로 묶는다.
